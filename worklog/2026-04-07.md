## 18. Dashboard approve relay: ping-then-send instead of fixed delay
**Files:** `extension/background.js`, `extension/manifest.json`, `/tmp/extension.zip`

User reported `Reddit dashboard approve failed: Content script not responding: Could not establish connection. Receiving end does not exist.`

**Cause:** the `RELAY_EXECUTE_TASK` handler waited a flat 1 second after `autopost.js` requested the relay, then sent `EXECUTE_TASK` directly. If the platform content script (`reddit.js`) wasn't fully initialized in that 1 second (slow page load, React not mounted), `chrome.tabs.sendMessage` hit a tab with no listener and Chrome threw the connection error.

**Fix:** ping-then-send pattern in `RELAY_EXECUTE_TASK`:
1. Send `SCROLL_DOWN` to the tab as a cheap "are you alive?" probe
2. Retry up to **10 times** with 2s delay (max 20s wait)
3. Only when the script responds, send the real `EXECUTE_TASK`
4. If the script never responds → return error `"Content script never responded after 20s — page may have redirected or script failed to inject"`
5. If it responds initially but disconnects mid-task → return error `"Content script disconnected mid-task: ..."`

This is the same readiness pattern already used by the auto-post `executeTask` flow (line 902), now applied to the dashboard approve relay path.

**What was NOT touched:** all content scripts, tab close logic, scrape paths.

## 15. "Last tab in window" guard — Chrome can no longer cascade-close
**Files:** `extension/background.js`, `extension/manifest.json`, `/tmp/extension.zip`

Even after section #14 (removing all `chrome.windows.*` calls), the user reported Chrome still auto-closing. Real root cause: **Chrome closes a window when its last tab is removed**, and exits when its last window closes. So `chrome.tabs.remove(taskTabId)` cascades to closing Chrome whenever the task tab happens to be the only tab in the only window.

This can happen if:
- The user has only one tab open and the extension's task tab is created in that same window
- The task tab finishes faster than the user opens any other tab
- Or the user happens to close all other tabs while the task is running

**Fix — "last tab" guard** in two places:

1. **`closeTab()` inside `executeTask`**: before removing, query all tabs in the same window. If `tabsInWin.length <= 1`, navigate the tab to `about:blank` instead of removing it. The harmless empty tab stays in the user's window. The next `cleanupStaleTabs` run (which has the same guard) will tidy it up once other tabs exist.
2. **`cleanupStaleTabs()`**: same logic — `chrome.tabs.get` → `chrome.tabs.query({windowId})` → if `<= 1` navigate to `about:blank`, else remove.

**What this guarantees:**
- The extension can never remove the last tab in a window
- Therefore can never close a window via tab removal
- Therefore can never trigger Chrome's "last window closed → exit" behavior
- The worst case is now: user sees an `about:blank` tab in their tab strip until they open something else or close it themselves

**What was NOT touched:**
- `executeTask` open path (still `chrome.tabs.create({active: false})`)
- Keep-alive interval, ping logic, timeouts, force-close
- All content scripts (Reddit/Quora/Skool/Pinterest/FB/Twitter)
- Scrape paths
- autopost.js fix
- The retry-on-create-fail flow

Only the close logic was modified — exactly the path that was breaking. Working pattern preserved.

- Extension version bumped **1.0.9 → 1.1.0**

## 13. Auto-post path also closing entire Chrome — second window-close bug
**Files:** `extension/background.js`, `extension/manifest.json`, `/tmp/extension.zip`

Section #11 fixed the dashboard-approve flow's `window.close()` bug. But user reported Chrome **still** auto-closing. Investigation found a second, separate bug in the **auto-posting** path (`executeTask` in `background.js`):

**Old `closeTab()` (line 875):** unconditionally called `chrome.windows.remove(t.windowId)` whenever a task finished. The intent was to close the offscreen task window the extension created via `chrome.windows.create`. But:

1. If `chrome.windows.create` failed (rate limited, OS denied, etc.), the fallback path used `chrome.tabs.create` which puts the tab in the **user's existing window** (line 866). When `closeTab()` then ran, it called `chrome.windows.remove` on the **user's window ID**, closing it — and Chrome itself if that was the only window.
2. Even on the happy path, the code never tracked which window we created vs which window the tab ended up in. Any race condition between window creation and tab placement could close the wrong window.

**Fix:**
- Added two tracked variables: `createdWindowId` (window WE created — safe to close) and `userWindowId` (user's pre-existing window — NEVER close)
- Rewrote `closeTab()` with strict guards:
  1. Get the current tab info
  2. If the tab's window ID matches `createdWindowId` AND that window only has our 1 tab → safe to call `chrome.windows.remove`
  3. If the window has other tabs (user opened them) → only `chrome.tabs.remove(tabId)`, leave window alone
  4. If we never created a window (fallback path used) → only `chrome.tabs.remove(tabId)`
  5. If anything fails or returns no tab → no-op
- Added explicit comment: NEVER call `chrome.windows.remove` on a window we didn't create

Audited the rest of `extension/` — `cleanupStaleTabs` and all scrape functions only use `chrome.tabs.remove` (safe). Only one `chrome.windows.remove` call remains in the codebase, and it's now properly guarded.

## 12. Quora false-failure verification fixed
**Files:** `extension/content/quora.js`, `extension/manifest.json`, `/tmp/extension.zip`

**Symptom:** Quora answers ARE actually being posted (user can see them on the platform), but the dashboard logs them as failed with `Answer submitted but not confirmed on page`.

**Root cause:** the post-submit verification was a single check after a fixed 4-second `sleep`:
1. Looked for the answer snippet in `body.innerText` — but Quora **navigates away** from the question page after a successful submit, so the original page no longer contains the text

**Fix — replaced single check with 12-second poll** that watches for any of 5 strong success signals:
1. **`url_changed`**: `window.location.href !== urlBefore` (Quora redirected — strongest signal)

3. **`editor_cleared`**: `editor.textContent.trim().length < 5` (editor reset)
4. **`submit_gone`**: submit button removed from DOM or disabled
5. **`text_on_page`**: snippet appears in current page innerText

The polling breaks as soon as any signal fires (typical case: 2–3 seconds). The result object now reports `verifyMethod` so we can see which signal worked when reviewing logs.

## 8. Reddit comment box: confirmed selector + multi-method paste
**Files:** `extension/content/reddit.js`, `extension/manifest.json`

User ran the probe script and the DOM dump confirmed:
- `shreddit-composer` is always present (no trigger click needed — editor is mounted on page load)
- The actual editor is `div[slot="rte"][contenteditable="true"][role="textbox"][data-lexical-editor="true"]` inside `shreddit-composer`
- Reddit uses **Lexical**, which silently ignores `ClipboardEvent('paste')` in many builds — that's why the previous "Paste failed" errors happened even though the editor was correctly found

**Rewrote `postComment()` New Reddit branch:**
- Removed the entire 80-line "find trigger / click placeholder / multi-strategy editor lookup" block — the probe proved it's unnecessary
- New flow:
  1. Find `shreddit-composer` (with scroll fallback if not in viewport)
  2. Inside it, grab `div[slot="rte"][contenteditable="true"]` (with fallbacks to `[data-lexical-editor=true]` etc.)
  3. Real `mousedown`/`mouseup`/`click` MouseEvents on the editor (Reddit React handlers ignore plain `.click()`)
  4. Place caret at end of editor via `Selection`/`Range` API
  5. **Insert text via 4 fallback methods, in order**:
     1. `document.execCommand('insertText', false, text)` — Lexical's preferred path
     2. `dispatchEvent(new InputEvent('beforeinput', { inputType: 'insertText', data }))` — alternative Lexical path
     3. `dispatchEvent(new ClipboardEvent('paste'))` — legacy fallback
     4. Direct `editor.innerHTML = '<p>...</p>'` + `InputEvent('input')` — last resort
  6. Verify `editor.textContent` length after each method, stop as soon as one works
- Error message now reports which methods failed: `"Paste failed — all 4 insertion methods produced empty editor (inserted=true/false)"`

- Extension version bumped **1.0.4 → 1.0.5** — reload in `chrome://extensions` to pick up the change.
